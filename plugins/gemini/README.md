# memsearch — Gemini CLI extension

Automatic, branch-scoped persistent memory for [Gemini CLI](https://github.com/google-gemini/gemini-cli).

## What it does

memsearch ships memory plugins for Claude Code, Codex, and OpenCode. Those are
**producers** — Claude Code and OpenCode summarize sessions into per-branch
markdown under `<memory-dir>/<repo>/<branch>/` (Codex currently writes a *flat*
`<memory-dir>/`, so v1 does not pick up Codex-only memory). This Gemini extension
is primarily a **consumer**: at `SessionStart` it injects the most recent
per-branch memory into the model's context.

The driving use case is **headless review**: when Syndic spawns Gemini
(`gemini --approval-mode auto_edit -p "..."`, cwd = target repo) to participate in
PR/branch investigation, the critic should start already aware of recent decisions
on the current git branch. `SessionStart` makes that happen with zero user action.

| Hook | Event | Behavior |
|------|-------|----------|
| `session-start.sh` | `SessionStart` | **Centerpiece.** Grep-pushes headings + bullets from the 2 most recent daily logs in the current repo/branch memory bucket into `additionalContext`. Read-only, ~0.08s, no Milvus. |
| `before-agent.sh` | `BeforeAgent` (≈ Claude's `UserPromptSubmit`) | Lightweight nudge that the `memory-recall` skill is available. Mostly for interactive sessions. |

**Recall** (semantic search of all history) is handled by the shared
`memory-recall` skill, which Gemini auto-discovers from `~/.agents/skills/`.

## Install

```bash
bash plugins/gemini/install.sh
```

Requires [memsearch](https://pypi.org/project/memsearch/) on `PATH` (or `uvx`).
Memory must already be populated by a sibling plugin for there to be anything to
inject — on a fresh repo/branch the hook degrades silently.

## v1 scope

Injection only. **Per-turn capture (writing Gemini's turns back into memory) is
intentionally deferred**: it requires a self-detaching background worker, and on
Windows that is the same process-reaping minefield the project documents
elsewhere. Gemini consuming a corpus the siblings populate is the high-value path
for headless review; capture is secondary for one-shot critics.

There is therefore **no watcher, no indexer, no single-writer lock, and no write**
in these hooks — strictly read-only.

## Why `hooks.json` is generated (not committed)

`gemini-extension.json` is committed; `hooks/hooks.json` is **generated by
`install.sh`** from `hooks/hooks.json.template` and is gitignored.

Gemini executes hook `command` strings through **`powershell.exe -NoProfile
-Command`** on Windows and **`/bin/sh -c`** on POSIX. A single command string
cannot be valid in both shells:

- **Windows (PowerShell):** a quoted executable path is not a runnable statement
  on its own — it throws `Unexpected token`. It must be invoked with the call
  operator: `& "C:/Program Files/Git/usr/bin/bash.exe" "${extensionPath}/hooks/session-start.sh"`.
  The Git Bash path is also machine-specific, so it cannot be committed.
- **POSIX:** `bash "${extensionPath}/hooks/session-start.sh"` (a leading `&` would
  be a syntax error).

`install.sh` detects the platform, resolves the running Git Bash via
`cygpath -m`, and substitutes the `@@LAUNCH@@` sentinel in the template. The
`${extensionPath}` variable is left intact — Gemini substitutes it at runtime.

`timeout` values in `hooks.json` are in **milliseconds** (Gemini default 60000).

## Layout

```
plugins/gemini/
├── gemini-extension.json     # committed manifest {name, version, description}
├── hooks/
│   ├── hooks.json.template   # committed; @@LAUNCH@@ + ${extensionPath} placeholders
│   ├── hooks.json            # GENERATED by install.sh (gitignored)
│   ├── common.sh             # stdin-cwd + per-branch bucket derivation; no watch
│   ├── session-start.sh      # centerpiece grep-push
│   └── before-agent.sh       # recall-skill nudge
├── scripts/
│   └── derive-collection.sh  # same collection-derivation logic as the siblings
├── install.sh
└── README.md
```
